1. System Overview & The Core Mission

MoneyHoney is a distributed financial market analytics, algorithmic trading, and quantitative data platform. Financial data platforms have fundamentally different requirements than typical web apps:

  • High-Frequency Ingestion: Historical 1-minute candle bars across 50+ major equities generate over 10GB of dense tabular data.
  • Strict Microservice Isolation: A slow analytical stock query must never block an urgent order execution on the Trades service or prevent a user from logging in on the Auth service.
  • Anti-Abuse & Boundary Protection: Financial endpoints are prime targets for credential-stuffing and DDoS attempts. The system must filter and rate-limit requests at the outermost perimeter.

2. Network Architecture & Traffic Flow

💡 Real-World Airport Analogy
Think of MoneyHoney like an International Airport:
  • Nginx (Port 80): The Airport Highway Entrance. Directs traffic, handles general traffic control, and gives quick information to drivers without letting them crowd the terminal.

  • Router: Dispatches to Auth (8001), Trades (8002), or Market LB (8003).

  • Metrics: Live inspection endpoint at GET /lb-status.

  • Database: Talks to SQL Server (Port 1433) via ODBC Driver 17.
  • Pagination: Uses B-Tree Clustered Primary Key cursor seeking ($O(1)$).

  • Endpoints: POST /login, POST /refresh.
  • Anti-Timing Attacks: Uses secrets.compare_digest for password checking.

  • Validation: Pydantic TradeBody strict schema checking.
  • Persistence: Writes to MHUsers table in SQL Server.
  • Transactions: SQLAlchemy session commit & rollback safety.

🗄️ Persistence: Redis + SQL Server Storage Layer

  • Redis (6379): Sub-millisecond volatile memory for rate limits & ticker query cache.
  • SQL Server (1433): Persistent storage of historical 1-minute bars & user tables.

⚡ Problem 2: Architectural Confusion & "Folder Hell"

System Design
The Challenge: When building a production-level API for the first time, developers get overwhelmed creating dozens of nested folders (routers, services, helpers, controllers, schemas) before understanding how they interact. This creates circular imports and mental paralysis.
The Solution: "Mental Map + Essentials Only" Principle.

We adhered strictly to domain-driven development: only create a file or directory when a concrete business domain demands it. We segregated the system into 3 distinct functional boundaries:

  • Identity: backend/gurd/auth.py
  • Market Data: backend/app/api/v1/endpoints/users.py
  • Orders: backend/app/api/v1/endpoints/trades.py

⚡ Problem 3: 10GB of Market Data Crashing Browsers & Servers

Performance & Big Data
The Challenge: A single stock has over 500,000 minute candles. The full database holds ~10GB of data. Loading this full dataset into browser memory crashes the browser tab immediately. Standard pagination with OFFSET 400000 LIMIT 20 causes SQL Server to perform an $O(N)$ full table scan, pegging server CPU at 100%.
The Solution: The 3-Tier Throughput Engine (Cursor Seeking + Redis Caching + Rust SIMD Serialization).
  1. Cursor Pagination ($O(1)$): Instead of OFFSET, we query WHERE id > cursor ORDER BY id LIMIT limit. Because id is the clustered primary key, SQL Server performs an instant B-Tree Index Seek straight to the target disk page in under 2ms.
  2. Write-Through Redis Caching: Results are cached with a 60-second TTL under ticker:{name}:cursor:{c}:limit:{l}. Subsequent requests hit Redis volatile memory in 0.5ms with an X-Cache: HIT header.
  3. SIMD Serialization with orjson: Bypasses Python's slow string encoders and serializes directly to UTF-8 bytes using CPU AVX2 instructions, streaming raw bytes straight to the client socket.

⚡ Problem 4: Independent Microservices vs. Single Ingress Port

Microservices Routing
The Challenge: Auth, Trades, and Users/Market Data are separate microservices running on different ports (8001, 8002, 8081). Clients (such as the Streamlit frontend or mobile apps) shouldn't have to keep track of multiple ports, IP addresses, or manage CORS across different hosts.
The Solution: Intelligent Path-Based API Gateway (Port 8000).

We built [`backend/gateway/main.py`](file:///C:/Users/PANRIT/ALL/Pranit%20Main/Study/python/API/Advance%20API/MoneyHoney/backend/gateway/main.py) which acts as the single public "front door":

  • Calls to /login or /refresh $\rightarrow$ Dispatched to Auth Microservice on Port 8001.
  • Calls to /trade or /mytrades $\rightarrow$ Dispatched to Trades Microservice on Port 8002.
  • Calls to /get_data or /watchlist $\rightarrow$ Dispatched to Market Data Load Balancer on Port 8003.

⚡ Problem 5: Rate Limiting & The Boundary Burst Exploit

Security & Anti-Abuse
The Challenge: Fixed-window counters (e.g. key reset at the start of each minute) allow clients to send 60 requests at second 59 and another 60 requests at second 01, blasting the server with 120 requests in 2 seconds without triggering the rate limit.
The Solution: Redis Sorted Sets (`ZSET`) Sliding Window Algorithm.

In [`backend/gateway/rate_limiter.py`](file:///C:/Users/PANRIT/ALL/Pranit%20Main/Study/python/API/Advance%20API/MoneyHoney/backend/gateway/rate_limiter.py), we track requests by timestamp in a rolling 60-second window. Expired timestamps are pruned atomically via ZREMRANGEBYSCORE, and cardinality is counted via ZCARD. If the client exceeds the quota, they receive an immediate HTTP 429 Too Many Requests with a Retry-After header.

⚡ Problem 6: Load Balancing Heavy Queries with Automatic Failover

Traffic Balancing
The Challenge: When dozens of traders chart historical data simultaneously, a single worker instance can become CPU-bound. Furthermore, if a worker crashes due to an out-of-memory error, the entire market data feed goes down.
The Solution: Self-Healing Async Load Balancer (Port 8003).

In [`backend/gateway/load_balancer.py`](file:///C:/Users/PANRIT/ALL/Pranit%20Main/Study/python/API/Advance%20API/MoneyHoney/backend/gateway/load_balancer.py), we implemented:

  • Thread-Safe Round Robin: Cycles between Worker #1 (8081) and Worker #2 (8082).
  • Background Health Prober: Every 5 seconds, an asynchronous loop tests /mh/v1/health. If a worker fails 2 consecutive checks, it is removed from the active pool. When it recovers, it is seamlessly reintegrated.

6. Under-The-Hood Mechanics (Low-Level Explanations)

A. Sliding-Window Rate Limiting using Redis Sorted Sets (`ZSET`)

💡 Security Camera Analogy
A fixed-window rate limiter is like taking a single photograph at 12:00 and another at 12:01. It has no idea what happened in between. A sliding-window rate limiter is like a continuous rolling security video that constantly looks back at the exact last 60 seconds from the current microsecond.

The Sorted Set data structure in Redis orders elements by a floating-point score. Here is the mathematical step-by-step:

  1. Current timestamp $T_{now} = 1728039600.550$.
  2. Window lower bound $T_{start} = T_{now} - 60 = 1728039540.550$.
  3. ZREMRANGEBYSCORE key 0 T_{start} removes all elements with score $< T_{start}$.
  4. ZCARD key counts all elements remaining in the window $[T_{start}, T_{now}]$.
  5. If count $< \text{limit}$, we allow the request and call ZADD key T_{now} member.
  6. If count $\ge \text{limit}$, we deny the request with HTTP 429 and calculate $\text{retry\_after} = \lceil T_{now} - T_{oldest} \rceil$.

B. Clustered Primary Key Index Seeking ($O(1)$) vs. Offset Scans ($O(N)$)

💡 Bookmarking Analogy
Imagine you are reading a 1,000-page book:
  • Offset Pagination: Every time you open the book to page 800, you are forced to flip through pages 1 to 799 one-by-one before reading page 800.
  • Cursor Pagination: You left a bookmark at page 800. You open directly to page 800 in 0.1 seconds.

In relational databases, primary keys form a Clustered B-Tree Index. The index nodes store sorted ranges of keys pointing directly to physical 8KB data pages on disk. By specifying WHERE id > :cursor LIMIT 20, the storage engine traverses the B-Tree in $O(\log N)$ tree depth (typically 3 or 4 page reads) and reads 20 contiguous rows sequentially from disk. Execution time remains under 2ms even if the table contains 10 million rows!

C. Rust SIMD Acceleration in `orjson`

Python's native json module serializes objects one field at a time using interpreted CPython loops. orjson is written in Rust and utilizes modern CPU SIMD (Single Instruction, Multiple Data) vector registers (AVX-512 / AVX2):

  • It escapes string characters and parses floating point numbers 16 or 32 bytes at a time in parallel inside CPU vector registers.
  • It generates raw UTF-8 encoded bytes directly, eliminating intermediate Python heap memory allocations.
  • FastAPI's Response(content=json_bytes, media_type="application/json") writes those bytes directly into the TCP socket send buffer, achieving 10x higher throughput under heavy load.

D. Constant-Time Cryptographic Comparison (`secrets.compare_digest`)

Why can't we use if password == "my_secret_pass":? The standard Python == operator short-circuits. If the first character doesn't match, it returns False immediately (say in 10 nanoseconds). If 5 characters match before a mismatch, it returns in 50 nanoseconds.

An attacker measuring latency across millions of requests can deduce the password character-by-character based on timing differences. secrets.compare_digest always evaluates every byte across the entire length of both strings, ensuring execution time is completely invariant to matches or mismatches.

E. The ASGI Event Loop & Socket Proxying

Uvicorn runs on an asynchronous event loop (backed by uvloop or asyncio). When the API Gateway receives an HTTP request:

  1. The OS notifies Uvicorn that data is ready on client socket file descriptor $S_1$.
  2. The gateway parses the HTTP headers and inspects the JWT token.
  3. It opens a persistent connection pool socket $S_2$ to the downstream microservice.
  4. Using httpx.AsyncClient.send(..., stream=True), the gateway yields execution back to the event loop while waiting for downstream packets, allowing a single Python process to handle thousands of concurrent requests without thread starvation!

Initiates a TCP socket connection to Redis on port 6379. Critical low-level detail: We configure socket_connect_timeout=0.5. If Redis is unreachable, the gateway fails fast in 500ms instead of hanging for the OS default TCP timeout (which is typically 30 seconds), instantly falling back to the in-memory store.
def is_rate_limited(self, identifier: str, limit: int = 60, window_seconds: int = 60): current_time = time.time() window_start = current_time - window_seconds
Epoch Window Calculation
Queries the OS kernel clock for the current Unix timestamp. Any recorded request with a timestamp earlier than window_start is now expired and must be evicted.
if self.redis_client is not None: try: key = f"ratelimit:{identifier}:{window_seconds}" pipe = self.redis_client.pipeline() pipe.zremrangebyscore(key, 0, window_start) pipe.zcard(key) pipe.zadd(key, {f"{current_time}_{time.time_ns()}": current_time}) pipe.expire(key, window_seconds + 5) results = pipe.execute() current_count = results[1]
Atomic Redis Pipeline Execution
Packages 4 Redis commands into a single TCP packet. zremrangebyscore purges expired members, zcard counts active hits, and zadd records the current hit salted with time.time_ns() to prevent hash collisions. results[1] extracts cardinality in $O(1)$ memory access.
if current_count >= limit: self.redis_client.zremrangebyrank(key, -1, -1) retry_after = max(1, int(window_seconds - (current_time - window_start))) return True, 0, retry_after remaining = max(0, limit - (current_count + 1)) return False, remaining, 0
Rate Limit Verdict & Rollback
If the request exceeded the limit, zremrangebyrank(key, -1, -1) deletes the entry that was just added so that denied requests do not artificially prolong the penalty window. Returns True along with the seconds to wait.
