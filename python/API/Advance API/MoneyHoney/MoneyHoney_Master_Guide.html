1. High-Level Blueprint & Overview

MoneyHoney is a distributed, high-performance financial market analytics and trade execution platform. It is engineered specifically to resolve the three fundamental bottlenecks of financial platforms:

  • Big Data Throughput: Handling over 10GB of 1-minute historical stock data (Nifty 50 stocks) without exhausting browser or server memory.
  • Microservice Segregation: Complete decoupling of the Auth Microservice, Trades Microservice, and Users & Market Data Microservice into autonomous runtimes.
  • Resilience & Anti-Abuse: An intelligent API Gateway enforcing sub-millisecond JWT authentication, atomic Redis sliding-window rate limiting, and an adaptive health-checking Load Balancer.

5. Low-Level Concepts & "What's Happening in the Background"

A. Sliding-Window Rate Limiting using Redis Sorted Sets (`ZSET`)

Most basic APIs use simple "fixed window" rate limiting (e.g. key `user:123:minute:10` = 50). Fixed windows suffer from the Boundary Burst Vulnerability: a client can send 60 requests at 10:00:59 and another 60 requests at 10:01:00, hammering your server with 120 requests in 2 seconds without violating the limit.

MoneyHoney implements a Sliding Window Rate Limiter backed by Redis Sorted Sets:

🧠 The Low-Level Math & Redis Operations
  1. Score & Member: Each incoming request is saved in a Redis sorted set with the floating-point Unix timestamp as the score: ZADD ratelimit:ip:192.168.1.1:60 1728039600.123 "1728039600.123_456789". The nanosecond salt ensures uniqueness so concurrent requests don't overwrite each other.
  2. Atomic Eviction: Before checking the limit, any request timestamp older than current_time - 60 is purged: ZREMRANGEBYSCORE ratelimit:ip:192.168.1.1:60 0 (now - 60). This takes $O(\log N + M)$ time.
  3. Cardinality Check: ZCARD ratelimit:ip:192.168.1.1:60 returns the exact number of requests made in the rolling 60-second window.
  4. Atomic Pipeline: All 4 commands (ZREMRANGEBYSCORE, ZCARD, ZADD, EXPIRE) run in a single Redis network roundtrip via pipeline.execute(), ensuring zero race conditions between concurrent threads.

B. Cursor Pagination vs. Offset Pagination on 10GB Data

When querying a 1-minute historical database with tens of millions of rows, standard pagination (OFFSET 1000000 LIMIT 20) causes catastrophic performance degradation. Why?

⚙️ Why `OFFSET` Destroys Database Performance
In standard SQL, OFFSET 1000000 forces the query engine to read 1,000,020 rows off the disk, sort them in memory, discard the first 1,000,000 rows, and return only the final 20. This is an $O(N)$ full table/index scan.
⚡ How MoneyHoney's Cursor Pagination Works ($O(1)$)
In [`users.py`](file:///C:/Users/PANRIT/ALL/Pranit%20Main/Study/python/API/Advance%20API/MoneyHoney/backend/app/api/v1/endpoints/users.py#L97-L101), we use: select(model).where(model.c.id > cursor).order_by(model.c.id).limit(limit). Because id is the clustered primary key index, the database engine executes a direct B-tree search (Index Seek) straight to the exact page where id == cursor and reads precisely limit rows. Execution time is identical whether you are at row 10 or row 10,000,000!

C. SIMD-Accelerated Serialization with `orjson`

Python's native json.dumps() is executed purely on the CPU via CPython bytecode, which becomes a severe bottleneck when serializing arrays of 25,000+ stock candles. MoneyHoney uses orjson:

  • Written in Rust, utilizing CPU SIMD (Single Instruction, Multiple Data) instructions (AVX2 / SSE4.2) to serialize JSON vectors in parallel.
  • Directly generates a UTF-8 encoded bytes buffer, bypassing the intermediate Python str allocation.
  • We return a raw fastapi.Response(content=json_data, media_type="application/json"), completely avoiding FastAPI's default jsonable_encoder which needlessly traverses Python dictionaries a second time.

D. Constant-Time Cryptographic Comparison (`secrets.compare_digest`)

In [`auth.py`](file:///C:/Users/PANRIT/ALL/Pranit%20Main/Study/python/API/Advance%20API/MoneyHoney/backend/gurd/auth.py#L68), when checking passwords, we do not use username == expected_user. We use secrets.compare_digest.

🛡️ Preventing Side-Channel Timing Attacks
The standard Python == operator compares strings character-by-character and halts immediately at the first mismatch. An attacker measuring latency over millions of requests with microsecond precision could discover the password character-by-character based on whether the server returned 401 in 1.1ms versus 1.2ms. secrets.compare_digest always evaluates every character in identical execution time, eliminating timing leaks entirely.

Epoch Window Calculation
Calculates the precise sliding time boundary. time.time() queries the OS kernel's monotonic/wall clock (via gettimeofday or clock_gettime). Any timestamp earlier than window_start is now invalid.
if self.redis_client is not None: try: key = f"ratelimit:{identifier}:{window_seconds}" pipe = self.redis_client.pipeline() pipe.zremrangebyscore(key, 0, window_start) pipe.zcard(key) pipe.zadd(key, {f"{current_time}_{time.time_ns()}": current_time}) pipe.expire(key, window_seconds + 5) results = pipe.execute() current_count = results[1]
Atomic Redis Pipelining
Constructs an atomic command buffer sent in a single TCP socket packet. pipe.zremrangebyscore sweeps away expired members. pipe.zcard measures current volume. pipe.zadd records the new hit with nanosecond salt (time.time_ns()). results[1] extracts the cardinality directly from Redis memory before this request.
if current_count >= limit: self.redis_client.zremrangebyrank(key, -1, -1) retry_after = max(1, int(window_seconds - (current_time - window_start))) return True, 0, retry_after remaining = max(0, limit - (current_count + 1)) return False, remaining, 0
Rate Limit Verdict & Rollback
If the request exceeds the limit, zremrangebyrank(key, -1, -1) immediately removes the request that was just added so denied requests don't artificially prolong the penalty window. Returns True with the exact seconds until quota resets.

7. Failure Modes & Self-Healing Scenarios

Scenario 1: Redis Crashes or Restarts
What happens: The API Gateway's SlidingWindowRateLimiter detects the socket connection failure within 500ms and switches seamlessly to the in-memory double-ended queue. In users.py, market data queries bypass the cache and query SQL Server directly. Result: Zero 500 errors returned to users.
Scenario 2: Market Worker #1 Crashes under Heavy Load
What happens: The Market Data Load Balancer detects that Worker #1 failed 2 consecutive health checks on /mh/v1/health. Worker #1 is instantly flagged as is_healthy = False and removed from the active round-robin pool. 100% of traffic routes to Worker #2. Once Worker #1 is restarted, the prober flags it healthy and restores it to the pool.
Scenario 3: Brute Force Attack on Login
What happens: An attacker sends 100 login attempts per second. The API Gateway detects the ip:{client_ip}:login key has reached its 10 req/min threshold. The 11th request is terminated at the gateway boundary with HTTP 429 Too Many Requests. The Auth microservice never sees the traffic, preserving its CPU cycles.
